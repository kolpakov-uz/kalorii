# Пищевая база

`nutrition.js` хранит исходные КБЖУ на 100 г отдельно от округлённых значений порции. Быстрый путь принимает только один однозначный продукт с явно указанным весом в граммах. Составные блюда, фото, несколько продуктов, порции и исправления обрабатывает ИИ. Строго различаются жирность, известная марка и приготовление. Неизвестная марка не заменяется известной. Для мяса и круп приложение один раз предлагает способ взвешивания, запоминает его по семейству продукта; явное уточнение всегда важнее. Сброс — в настройках.

Новая оценка сохраняется сразу. Она остаётся приблизительной и через семь дней перестаёт использоваться локально без нового расчёта. Ручные значения из «Моих блюд» и явно названные КБЖУ на 100 г сохраняются как персональные поправки, не истекают и не переписываются справочником. Изменение только граммов не меняет базовые значения. Дневник прошлых дней не пересчитывается при обновлении справочника.

Выбор веса предлагается для неоднозначных круп и куриного филе по целым словам: «греческий йогурт», рисовые хлебцы, овсяное печенье и готовые блюда не считаются сырой крупой. Указанное приготовление и отрицание («не жареная») важнее сохранённого выбора; сыр, варенье и вареники не обозначают способ приготовления. «Вернуться к вводу» закрывает вопрос и сохраняет черновик. Процент съеденной порции отделён от жирности продукта. Миллилитры не пересчитываются локально как граммы: их интерпретирует ИИ с учётом продукта. Марки молочных продуктов проверяются при сопоставлении с «Моими блюдами»; варианты без марки не заменяются брендированными. Старые ключи пищевого кэша сверяются по названию, без пересчёта дневника и перезаписи ручных значений.

Личный кэш хранится на устройстве и под префиксом `nutrition:v1:user:<verified Telegram ID>` в существующем KV SUBS. Авторизация совпадает с приложением; клиент не выбирает владельца. Дневник и переписка не выгружаются через режим `nutrition`. Синхронизация кэша не является синхронизацией всего дневника. KV имеет eventual consistency: первичен локально сохранённый результат; при отсутствии сети приложение продолжает работать с доступными данными. База ограничена 1000 продуктами на аккаунт.

Начальный справочник `nutrition-seed.js`: десять точно сопоставленных позиций USDA Foundation Foods (октябрь 2026). У каждой позиции сохранены FDC ID, ссылка и дата проверки. Это ограниченное начальное покрытие, а не полная база продуктов Узбекистана. Нельзя сопоставлять US cottage cheese с местным творогом без проверки состава. Домашние рецепты и продукты без точного совпадения остаются оценками.

Существующий минутный cron пушей сохранён. В 17-ю минуту каждого часа запускается обслуживание питания: USDA проверяется раз в семь дней, недоступный источник — снова через час. Загружается только Foundation JSON с официального домена, с ограничением размера и времени. Для личных продуктов выполняется максимум пять точных поисков Open Food Facts за час, каждый продукт проверяется не чаще раза в неделю. Несколько совпадений, отсутствие бренда, другая жирность или неполные КБЖУ отвергаются. Новые позиции могут получить источник раньше недельного срока при первом обслуживании. Источник, не содержащий продукт, нельзя заменить выдуманной ссылкой. Брендовые значения проверяйте по этикетке; пользовательская база OFF не гарантирует точности.

Источники и лицензии:

- [USDA FoodData Central](https://fdc.nal.usda.gov/) — public domain, CC0. Авторство указано в настройках. [Загрузки](https://fdc.nal.usda.gov/download-datasets/).
- [Open Food Facts](https://world.openfoodfacts.org/) — ODbL 1.0 для базы, DbCL для содержимого. Атрибуция в настройках. Производные данные OFF сохраняют эти условия при передаче, в том числе при экспорте личной резервной копии. Изображения OFF приложение не использует. [Условия повторного использования](https://openfoodfacts.github.io/openfoodfacts-server/api/tutorials/license-be-on-the-legal-side/).

## Резерв AI

`worker/groq.js` активен только при наличии секрета `GROQ_API_KEY`. Без него остаётся прежняя очередь Gemini. Ключ не входит в клиент или Git. Для текста — production-модель `openai/gpt-oss-20b`. Для фото и уточнений с изображением включена `qwen/qwen3.8-27b` через `GROQ_VISION_MODEL`: доступность и бесплатная квота проверены реальным запросом проекта. Модель находится в preview; при её отказе остаётся Gemini. Платёжные данные не добавляются.

Для текста Gemini запускается первым, через 700 мс при задержке — резерв; при ошибке основного провайдера резерв стартует сразу. Для фото оба маршрута стартуют сразу, без этой задержки. Vision использует короткую инструкцию с тем же форматом действий и `reasoning_effort: none` и `temperature: 0`, сохраняя изображение, текущую подпись, id записей и историю этой задачи. Распознавание и приблизительные КБЖУ возвращаются одним вызовом. Принимается первый полностью проверенный ответ; обрезанные ответы Groq отбрасываются. Остальные сетевые попытки отменяются. Это может расходовать квоты двух провайдеров; отмена не гарантирует возврата уже потраченной квоты. Действия в дневнике выполняются только после выбора одного результата. Голосовой ввод по-прежнему использует Gemini. Сбои резерва не отключают основной маршрут. Внешнему провайдеру передаётся описание/фото и контекст именно этой задачи.

Фото без подписи позволяет оценить тип блюда и обычную порцию. Точный вес, жирность фарша, масло и марку нельзя достоверно определить по одному снимку. Приблизительность обозначается в ответе. Для исправления пользователь нажимает «Уточнить блюдо» у нужной записи: новая реплика относится к той же задаче. После успешного распознавания простой вес одной записи меняется локально; исправление состава отправляет сохранённые записи как текст, без повторной платы токенами за изображение. Для явного «пересчитай по фото» и повторов неудачного распознавания исходное фото передаётся снова. В видимой переписке и резервной копии снимок сохраняется.

Известный продукт рассчитывается на устройстве. Для нового блюда или фото нельзя гарантировать ответ внешнего бесплатного API за две секунды.

Для читаемой этикетки AI передаёт отдельное поле `label`: вес базы (`basisGrams`), энергию с единицей `kcal` или `kJ` и БЖУ для этой базы. Если обе единицы напечатаны, отдельное поле printedKcal имеет приоритет: несовпадающие после перевода кДж не заменяют напечатанные ккал. Перевод кДж в ккал при отсутствии ккал (деление на 4.184), перевод порции этикетки к 100 г и пересчёт съеденного веса выполняет код. Надпись «жир в сухом веществе» не равна граммам жира на 100 г. БЖУ внутри label необязательны: отсутствующее на этикетке значение не превращается в ноль. Для него сохраняется отдельная приблизительная оценка AI, а ответ сообщает, какие показатели не были прочитаны. Если нельзя прочитать энергию, единицу или вес базы, label не передаётся.

До выбора победившего AI-ответа проверяются пределы КБЖУ и грубое превышение энергии относительно 4/9/4. Это мягкая проверка очевидных ошибок единиц, а не замена энергии этикетки формулой: клетчатка, полиолы и алкоголь требуют допусков. На клиенте проверяется также частичное исправление с учётом остальных значений записи. Некорректная оценка не записывается и не переиспользуется из старого кэша. Свежий расчёт с фото не подменяется оценкой из справочника; явно сохранённые ручные значения остаются приоритетными. История дневника автоматически не переписывается: ранее ошибочную запись нужно пересчитать через «Уточнить блюдо» → «Пересчитай по фото».

Проверки: `node --test scripts/nutrition.test.mjs scripts/groq.test.mjs scripts/food-photo.test.mjs`; также входят в обычную публикацию.
