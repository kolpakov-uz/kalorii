# Калории

[Открыть приложение](https://kolpakov-uz.github.io/kalorii/)

Статическое приложение для дневника питания. Интерфейс находится в `index.html`, браузерные уведомления — в `sw.js`, серверная логика Gemini и push-уведомлений — в `worker/index.js`.

## Веб и Telegram

Обе версии поддерживаются. Для самостоятельного входа через Safari, другой браузер или установленную иконку один раз получите код кнопкой «Веб-версия» в Telegram-приложении и вставьте его на сайте. Браузер запоминает доступ, прежний дневник сохраняется. [Подключение и модель доступа](docs/telegram.md#самостоятельная-веб-версия).

## Мои блюда

В настройках можно создать или изменить карточку блюда: название и его варианты, КБЖУ на 100 г, порцию быстрого добавления и показ в каждом из четырёх приёмов пищи. Закреплённые блюда появляются сразу, остальные — после 10 действующих записей в дневнике суммарно за все приёмы пищи. Для автоматически созданной карточки приёмы пищи определяются по дневнику; после ручной настройки выбор сохраняется. Удерживание блюда над полем ввода открывает редактирование, закрепление и удаление.

`dish-catalog.js` связывает записи с устойчивым ID, `my-dishes.js` управляет карточками. При обычном запросе дневника Gemini сопоставляет название со списком известных блюд и возвращает `foodId`; отдельного запроса к ИИ для этого нет. Список ограничен 100 карточками с приоритетом закреплённых. Ранее накопленные разные формулировки можно объединить в редакторе: исторические записи сохраняют прежние порции и КБЖУ, их количество учитывается вместе. Удаление скрывает карточку, сохраняя дневник; ручное добавление того же названия позволяет восстановить её. Резервная копия версии 1 сохраняет новые поля и читает прежние копии.

Проверки каталога, миграции, интерфейса и схемы Gemini входят в `scripts/publish.ps1`; отдельно: `node --test scripts/dish-catalog.test.mjs scripts/my-dishes.test.mjs scripts/dish-identity.test.mjs scripts/food-photo.test.mjs`.

## Независимые расчёты еды

Каждое новое описание блюда и каждое новое фото начинают отдельную задачу в текущем окне дневника. Одновременно обрабатываются две задачи, остальные ждут в очереди. Уточнения одной задачи выполняются последовательно; явный выбор «Уточнить» под ответом позволяет вернуться к более старому блюду. Короткие уточнения вроде «50 г», «попробуй ещё раз» и «исправь вес» продолжают последнюю задачу. Новые самостоятельные описания не получают прежнюю переписку или фото. Личный справочник блюд остаётся доступным для сопоставления названий.

`food-tasks.js` разделяет историю по `thread` и запросы по `task`, ограничивает параллелизм и сохраняет связи при переносе дневника. ИИ получает только записи выбранной задачи, а клиент отклоняет попытки изменить посторонний ID. Ответы могут приходить в разном порядке: они обновляют собственные сообщения и исходный день/приём пищи. Продолжение после сбоя восстанавливает собственный текст и фото. `requestId` изолирует неполные ответы и локальные таймауты в `gemini:cooldown:v3:`; реальные квоты, ограничения частоты и перегрузки модели остаются общими. Отдельные задачи не создают дополнительные квоты Gemini. Проверки: `node --test scripts/food-tasks.test.mjs scripts/food-photo.test.mjs scripts/gemini.test.mjs`.

## Публикация

GitHub Pages автоматически публикует корень ветки `main`. Worker `kalorii-ai` публикуется через Wrangler с конфигурацией `worker/wrangler.jsonc`.

На настроенном компьютере из папки репозитория:

```powershell
npm.cmd --prefix worker ci
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish.ps1 -CheckOnly
```

После проверки и коммита изменений:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish.ps1
```

Скрипт проверяет исходники, собирает Worker без публикации, требует чистую ветку `main`, проверяет удалённую ветку, публикует Worker и отправляет код в GitHub. После завершения нужно дождаться успешной сборки Pages. Публикации Cloudflare и GitHub не являются одной транзакцией: ошибка второго этапа оставляет уже опубликованный Worker.

Для изменения только приложения достаточно проверок, коммита и `git push origin main`; обновление Worker выполняется, когда меняется серверная логика или нужен совместный выпуск.

## Cloudflare

Конфигурация перенесена из действующего Dashboard, включая существующее KV-хранилище `SUBS` и расписание раз в минуту. Секреты `GEMINI_KEY` и `VAPID_KEY` остаются в Cloudflare. `keep_vars` сохраняет дополнительные переменные, заданные в Dashboard.

Авторизация сохранена локально и не включена в репозиторий. На другом компьютере потребуется вход в GitHub и Cloudflare:

```powershell
git credential-manager github login --device --no-ui
cd worker
.\node_modules\.bin\wrangler.cmd login --device --browser=false --use-keyring
```

Дальнейшие изменения Worker следует вносить в репозиторий. Если код или настройки изменены через Dashboard, перед следующим выпуском их нужно сверить с локальными файлами.

## Модели Gemini

Worker использует очередь `gemini-4-hydrogen` → `gemini-3.8-flash` → `gemini-3.5-flash-lite` для дневника, фото, чата тренера и голоса. Очередь задаётся в `worker/wrangler.jsonc` переменными `MODEL` и `MODEL_FALLBACKS`. Google предлагает бесплатный API-доступ к этим моделям в пределах квот проекта. Фактическая доступность определяется ответом API с действующим ключом.

При исчерпании суточной квоты модель пропускается до следующего календарного дня в `America/Los_Angeles`. Короткие ограничения учитывают `Retry-After` или `RetryInfo`, отказ в доступе к конкретной модели и отсутствие модели проверяются повторно через пять минут. Следующая доступная модель получает исходный запрос с тем же фото или аудио. Сетевые сбои, ошибки сервера и неполные ответы пропускаются на 30 секунд. Если суточные квоты исчерпаны у всей очереди, расчёт приостанавливается.

Схема ответа дневника явно описывает название, вес и все четыре показателя КБЖУ для добавления. Сервер проверяет содержимое успешного HTTP-ответа до выбора модели. При отсутствующих данных, сломанном JSON или обрыве генерации он переходит к следующей модели в том же запросе. Отказ по безопасности остаётся окончательным. Текстовые расчёты используют низкий уровень рассуждения новых моделей, фотографии и тренер — средний. Для дневника и тренера на попытку одной модели отводится до 8 секунд, на серверную очередь — до 24 секунд; для голоса — до 12 и 36 секунд соответственно. Ожидание каждой операции KV ограничено 250 мс. Автоповторы запросов дневника и тренера в приложении разделяют общий срок 45 секунд, включая паузы.

Для каждого действия тренера задана отдельная схема с его полями. Это ограничивает сложность схемы для API и делает параметры тренировки обязательными. Разные длительности силовой и кардио записываются отдельными тренировками с общей датой. Сервер проверяет весь ответ до отправки клиенту, клиент проверяет тренировки до применения набора действий. Автоповтор меняет только транспорт и разбор ответа, успешные действия применяются один раз. Регрессии записи через реальный обработчик чата, повторов и отмены входят в `scripts/coach.test.mjs`.

Состояние ограничений хранится в `SUBS`, отдельно для каждой модели и SHA-256 отпечатка API-ключа. Префикс `gemini:cooldown:v1:` сохраняет общие квоты, ограничения доступа и подтверждённые ошибки сервера модели. Префикс `gemini:cooldown:v2:` разделяет неполные ответы, локальные таймауты и сетевые сбои по режимам: еда, тренер, голос. Неудачный разбор еды не блокирует распознавание речи. Записываются только категория ограничения и срок. При недоступности всей очереди `retryAfter` сообщает остаток ожидания до первого доступного повтора уже в первоначальном ответе. Новый запрос после восстановления квоты снова начинает с приоритетной модели. Каждый переход к другой модели создаёт дополнительный вызов API. Проверки очереди и восстановления входят в публикацию, отдельно запускаются командой `node --test scripts/gemini.test.mjs`.

## Голосовой ввод

Пищевая база, разделение продуктов по марке/жирности/приготовлению, еженедельные источники и необязательный бесплатный резерв Groq описаны в [NUTRITION.md](NUTRITION.md).

При временной ошибке сервиса, сети, таймауте или кратком ограничении частоты запрос повторяется автоматически один раз. Пауза отсчитывается от ответа сервера, учитывает JSON `retryAfter` и HTTP `Retry-After` и составляет не менее 5,2 секунды. Обратный отсчёт можно отменить. При паузе больше 30 секунд доступен ручной повтор, который также соблюдает оставшееся ожидание; при исчерпанной дневной квоте и постоянных ошибках автоматического повтора нет. Между последовательными фрагментами сохраняется интервал не менее 5,2 секунды. Каждый повтор может расходовать квоту Gemini. Если сбой сохраняется, аудио остаётся только в памяти текущего окна, а кнопка «Повторить» продолжает с нераспознанного фрагмента. Успешные части сразу добавляются в редактируемое поле без повторного добавления при следующей попытке. Уведомление различает квоту, частоту запросов, недоступность сервиса, таймаут и ошибку разбора ответа и упоминает оставшийся текст только при непустом поле. Отмена, новая запись, закрытие панели, смена раздела или уход в фон удаляют сохранённое для повтора аудио. Проверки API с реальным обработчиком находятся в `scripts/voice-api.test.mjs`.

Микрофон рядом с отправкой доступен в дневнике и чате тренера. Повторное нажатие останавливает запись и запускает расшифровку; результат добавляется к текущему тексту, остаётся редактируемым и не отправляется автоматически. Автоматического ограничения длительности нет. Длинное аудио после остановки разбивается на последовательные WAV-фрагменты до 28 секунд (по возможности на паузах), без обрезки и потери хвоста. Они отправляются последовательно с паузами для соблюдения квоты, тексты собираются по порядку в один черновик. Память устройства, доступность сервиса и квоты Gemini остаются техническими ограничениями. Отмена, закрытие окна, переход между разделами или уход приложения в фон прекращают запись. Требуются HTTPS, разрешение микрофона, MediaRecorder и OfflineAudioContext; формат записи выбирается браузером, затем преобразуется в WAV 16 кГц mono PCM.

`voice.js` управляет записью, звуковым анализатором и черновиком, `worker/voice.js` проверяет WAV-фрагменты и формирует запрос `transcribe` к действующей модели Gemini. Аудио не сохраняется приложением в дневнике или KV; для расшифровки оно передаётся Gemini с действующим ключом. Расшифровка расходует один запрос Gemini на фрагмент, последующая отправка сообщения — ещё один. Волны вокруг круглой кнопки получают амплитуду из RMS сигнала микрофона через Web Audio: в тишине затухают до нуля. Граф анализатора не соединяется с динамиками. При остановке, ошибке или отмене освобождаются треки, AudioContext, таймеры и кадры анимации. При недоступном микрофоне текстовый ввод остаётся доступным. Автотесты: `node --test scripts/voice.test.mjs`; они включены в публикацию.
